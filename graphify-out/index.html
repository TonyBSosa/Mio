MIO / MAPA DEL PROYECTO

De una pieza disponible
a una venta organizada.

MIO ayuda a una tienda a organizar sus clientes, productos y pedidos de ventas por redes sociales. El vendedor puede registrar una venta directa o asociarla a un live. El comprador puede explorar el catálogo y solicitar un apartado.

Cómo ocurre una venta

Registro directo, con live opcional

  1. Preparar. El vendedor registra al cliente y la pieza. Si usará un live, crea o activa el evento.
  2. Registrar el pedido. Selecciona cliente y pieza, o escribe el producto. Un live es opcional; si lo selecciona, debe estar activo.
  3. Controlar disponibilidad. Si el pedido referencia una pieza del catálogo, el servidor comprueba que esté disponible y la aparta.
  4. Dar seguimiento. El pago pasa de pendiente a pagado y la entrega de pendiente a entregado. Los resúmenes consultan los pedidos.

La transmisión ocurre fuera de MIO. Aquí se organiza la venta; no se capturan automáticamente comentarios de redes sociales.

Del catálogo al comprobante

  1. Solicitar. El comprador inicia sesión y pide una pieza disponible. Se crea una solicitud pendiente; aún no es un pedido pagado.
  2. Confirmar. El vendedor confirma la reserva. En el entorno de pruebas habilitado, se bloquea la pieza y se asigna un plazo de 3 o 7 días.
  3. Revisar el comprobante. El comprador adjunta la imagen. El vendedor la aprueba o rechaza manualmente; se permite una corrección tras el primer rechazo.
  4. Crear el pedido pagado. Al aprobar el comprobante, el código crea el pedido con entrega pendiente. Si vence una reserva elegible sin comprobante, la lógica de expiración puede liberar la pieza.

Restringido a pruebas aisladas. La confirmación, la carga y revisión de comprobantes y la expiración tienen condiciones de entorno en el servidor. La existencia de pantallas no significa que el flujo esté habilitado para pagos reales.

Seis áreas para orientarte

1. Acceso y permisos — quién puede hacer cada cosa

El comprador ve su perfil y solicitudes; el vendedor administra su operación; el administrador gestiona usuarios. Angular controla la navegación y el backend valida la sesión, el rol y, donde corresponde, la pertenencia del registro.

El inicio de sesión crea una sesión y un JWT de 30 minutos. Un cliente del directorio comercial no equivale necesariamente a una cuenta de comprador.

  • Rutas y roles de la interfaz
  • Registro e inicio de sesión
  • Validación de sesión en la API
2. Catálogo y tienda — qué se ofrece

El vendedor administra piezas con código, precio y estado, y mantiene su perfil público. El catálogo muestra la oferta de la tienda. Una pieza puede dejar de estar disponible por un pedido o por una reserva confirmada.

Conecta con: solicitudes del comprador, pedidos del vendedor y la comprobación de vencimientos.

  • Reglas de productos
  • Catálogo público
  • Datos y estados de una pieza
3. Clientes y lives — a quién y en qué evento se vende

El directorio guarda los clientes del vendedor. Un live agrupa ventas de un evento; no transmite video. El pedido siempre necesita cliente, pero puede existir sin live para admitir venta directa.

  • Gestión de clientes
  • Gestión de eventos live
  • Validación del cliente y del live al vender
4. Pedidos — el centro del seguimiento

Relacionan vendedor, cliente, producto y live opcional. Conservan precio, cantidad y dos estados separados: pago y entrega. Pagar un pedido no implica que ya fue entregado.

La creación directa de un pedido y el bloqueo de la pieza son operaciones separadas con lógica de compensación. El flujo de aprobación de comprobantes utiliza una transacción; son mecanismos distintos.

  • Crear y actualizar pedidos
  • Consultas y bloqueo de piezas
  • Estructura persistida del pedido
5. Apartados y comprobantes — reservar antes de pagar

Una solicitud expresa interés. Al confirmarla se reserva la pieza; al aprobar el comprobante se genera el pedido pagado. Rechazar una solicitud pendiente la elimina en el código actual. La cancelación de una reserva confirmada requiere condiciones adicionales.

Expiración, comprobantes y pedidos comparten la disponibilidad del producto. Por eso este recorrido cruza más áreas y exige cuidado al modificarlo.

La política de pruebas aisladas limita su uso. El análisis no ha conectado servicios externos ni comprobado la configuración de producción.

  • Solicitud y confirmación
  • Carga, revisión y creación del pedido
  • Vencimiento y liberación de piezas
  • Condiciones que habilitan las pruebas
6. Resúmenes y documentación — entender el resultado

Dashboard y resumen presentan información derivada de los pedidos. Los documentos explican requisitos, decisiones y avances, pero algunos describen versiones anteriores o propuestas.

Para saber qué hace hoy una operación, conviene empezar por el servicio y el modelo actuales; después usar la documentación para entender la intención.

Dónde empezar a leer el código

Para seguir una petición: pantalla → servicio Angular → ruta de la API → controlador → servicio de negocio → repositorio o modelo. La API reúne sus rutas en expressApp.js. Algunos servicios, como comprobantes, acceden directamente a los modelos.

El cambio con más conexiones es la disponibilidad de una pieza: afecta al catálogo, la venta directa, la confirmación de reserva, la aprobación del comprobante y la expiración.
